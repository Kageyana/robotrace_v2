# 走行ログのバイナリ保存とCSV一括変換

## 保存と走行の流れ

走行開始準備で番号を予約し、`<番号>.tmp` を新規作成する。先頭512 Bを予約し、ビッグエンディアン記録を512 B整列の既存バッファで追記する。通常108 B、詳細145 Bの記録を保存する。2026-10-07に通常ログ末尾へ左右電流を追加した（従来100 B）。IMU温度は両プロファイルの既存列を使用する。

停止後の `endLog()` は残バッファを排出し、記録の有効長へ切り詰める。記録を読み、データCRC・クロス区間・一次経路検証を取得する。停止時の設定、校正、電圧、停止理由、ゴール位置、走行モード、参照番号をCSVメタデータと同じ文字列で保存する。ヘッダを確定して同期・クローズし、成功した場合だけ `.bin` へ変更する。

オートスタート1～4走目はバイナリ保存成功と必要な一次検証を確認して次走へ進む。DISTANCE、SLIP、PATH、SHORTCUTはバイナリを直接解析する。バイナリが欠落した場合だけ、従来CSVの列名による読込を使用する。不正バイナリがある場合は解析を失敗にする。

全5走終了、手動走行終了、緊急停止、途中の解析・保存失敗などによる連続走行打切りでは、保存完了済みの全未変換ログを番号順でCSV化する。緊急停止では機体停止を先に実行する。現在の走行の保存が失敗した場合、その `.tmp` は保持し、先行走行の確定済みログを変換する。

## バイナリ形式 v1

先頭512 Bのコンテナ整数はリトルエンディアン。記録部は既存のビッグエンディアン形式であり、C構造体のpaddingを保存しない。

| オフセット[B] | サイズ[B] | 内容 |
|---:|---:|---|
| 0 | 4 | ASCII `RLOG` |
| 4 | 4 | コンテナバージョン、1 |
| 8 | 4 | ログ番号、1～32767 |
| 12 | 4 | プロファイル、通常1・詳細0 |
| 16 | 4 | 記録サイズ、現行通常183／詳細220。固定旧形式は108／145／157／194／183／220 |
| 20 | 4 | 行数、0～65535 |
| 24 | 4 | 停止時メタデータのバイト数、末尾改行を含みNULを含まない |
| 28 | 4 | 記録部CRC32/IEEE |
| 32 | 4 | メタデータCRC32/IEEE |
| 36 | 4 | スキーマ識別CRC |
| 40 | 4 | オフセット0～39のヘッダCRC32/IEEE |
| 44 | 468 | 予約、0 |
| 512 | 行数×記録サイズ | 記録部 |
| 記録部の直後 | メタデータ長 | 保存済みCSVメタデータ1行 |

CRC32/IEEEは反射多項式 `0xedb88320`、開始値・終了XORは `0xffffffff`。スキーマ識別は `derived-v1;` と、列順の `型:列名;` を連結した文字列のCRCで、派生列も含む。追加計算の意味を変更した場合は派生計算版も更新する。

読込時は形式・番号・プロファイル・スキーマ・記録サイズ・行数・実ファイル長・各CRCを検証する。メタデータは4096 B未満で末尾改行が必須。現行通常72列・183 B／詳細87列・220 Bに加え、旧3世代の通常／詳細6形式を固定定義で受け入れる。プロファイル・スキーマCRC・記録サイズが対応表の組に一致する場合だけ、いずれの現行ビルドからも読める。未知のスキーマは拒否し、元バイナリを保持する。固定列は`log_schema_legacy.h`、`log_schema_shadow_v2.h`、`log_schema_candidate_v1.h`。読込用は最大220 Bを確保する。43列整理期間の履歴は[通常ログ43列への整理](light-log-43-columns.md)、現行への復帰は[通常ログ72列への復帰](log-72-restored.md)。

CSVには変換元の `binaryLogNumber`、`binaryDataCrc`、`binarySchema` を追加する。CRCのCSV表記は符号付き32bitだが、比較ではビット列として扱う。CSV列名・数値書式・単位は従来どおり。

ラインセンサー校正値は校正完了後の`initLog()`で走行別にコピーし、`endLog()`で`lSensorMax0`～`lSensorMax9`、`lSensorMin0`～`lSensorMin9`、`lineSensorCalibrationValid`としてメタデータへ確定保存する。値は正規化前のLED点灯・消灯差分AD値（0～4095）、センサー0は左端。有効フラグは1が有効。CSV変換時は現在のRAMや`lsval.txt`を参照せず、バイナリに保存済みの値をそのまま出力する。メタデータの追加なのでコンテナ版・スキーマCRC・記録サイズは変えず、項目を持たない旧ログも従来どおり読み込む。旧ログの欠落項目を0や異常校正と解釈しない。

この追加は通常・詳細の保存／遅延変換テストで、開始後のRAM値変更と保存後の走行別コピー消去を挟んでも各CSVに元の20値と有効フラグが残ることを確認した。変更後最初の実機CSVでは21項目の存在、値域、`max>min`、センサー順を確認する。実機ログによる確認は未実施。

## CSV確定と中断復旧

1. 読込・CRC検証・クロス区間抽出を行う。
2. 保存済みメタデータと既存列名を `<番号>.part` へ書く。
3. 共通計算による曲率・直線化・XYを従来書式で出力する。
4. 全行書込、同期、入出力ファイルのクローズを確認する。
5. `.part` を正式CSVとして確定する。既存CSVがある場合はメタデータCRCが一致する場合だけ置換する。
6. 元の `.bin` を削除する。

変換の途中失敗では元バイナリを保持する。CSV確定後のバイナリ削除に失敗した場合も成功扱いにせず、起動時に再変換する。同一ログの既存CSVを置換する途中で電源断しても、バイナリから作り直せる。別ログの同番号CSVは上書きしない。

起動時はSDと表示の初期化後、設定読込・CSV一覧整理前に未変換 `.bin` を復旧する。`.part` は対応する `.bin` から再作成する。未確定 `.tmp` は保持して警告し、自動昇格しない。対応するバイナリのない `.part` も勝手に削除せず、その番号を予約済みとして扱う。復旧失敗時は新規走行を禁止する。SD未挿入時の既存運用は維持する。

採番は数字だけの `.csv`、`.bin`、`.tmp`、`.part` と保存番号を調べ、最大番号の次を予約する。上限到達・列挙I/Oエラー時は作成を失敗にする。未変換バイナリは古いCSV整理の対象にならず、復旧失敗中はCSV自動整理もしない。

## 表示と責務

変換中は `CSV 2/5`、`Log 12931`、`Analyze / Write / Commit / Done / Failed`、処理段階の行数％、全体％を表示する。全体進捗は各ログの解析・出力行数と確定1単位から計算し、最後のCSV確定と元バイナリ削除が成功するまで100％にしない。

手動走行ではCSV変換成功後に走行タイム画面（バッファあふれ時はエラー画面）を表示して操作待ちに入る。変換失敗時は進捗の失敗画面を保持する。オートスタート5走の完了時は変換成功後に `Auto run Finish!` を表示する。

通常の進捗表示は最大5 Hzに抑え、対象番号・段階変更時は転送可能になり次第更新する。連続DMAは停止要求だけを出し、転送中なら表示を見送ってCSV変換を継続する。画面を専用の静的バッファ1024 Bへコピーし、アドレス設定コマンドと全画面を単発DMAで送る。完了割り込みでは次のDMA開始と完了通知だけを行い、従来のページごとの同期コマンド送信は使わない。HALのDMA開始に必要なアドレス送信処理は残るが、全画面の転送完了は待たない。開始失敗・転送中でも保存処理は継続し、最終のDone／Failedは保持する。CSV変換完了後だけ、最大200 msの転送待機と最終結果の表示を行って従来の連続DMAへ戻る。

変換は停止中のメイン処理で同期実行し、モーター出力0を維持する。開始操作を処理するメインループには変換完了まで戻らない。1 ms割り込みに新しいSD処理・表示処理・CRC計算を追加しない。

共通読込APIは `logSource.h` に分離し、FatFsロック下で1ファイルずつ使う。ヘッダ用RAMと既存ログバッファを停止中に再利用し、全走分をRAMへ保持しない。SD未挿入、制御ゲイン、安全条件、時刻記録形式は変更していない。

使用中の `STM32F446XX_FLASH.ld` は `_Min_Stack_Size` を1 KiBから8 KiBへ変更した。Debug逆アセンブルではCSV変換のローカルフレーム2592 B、書式化532 B、既存CSV照合632 B、記録走査404 Bを確認した。下位のFatFs・newlib・割り込みを含む実測最大値は未取得だが、既知のフレームより小さい予約のままヒープが伸びる状態は解消する。生成された他の未使用リンカスクリプトは変更しない。

## 検証

2026-10-12、exFATの起動時復旧でFatFs R0.12cの`f_open()`通常成功経路に`obj.n_frag`の初期化がないことを実機で確認した。スタック上の未初期化値を`f_lseek()`の`fill_last_frag()`が参照し、メタデータ位置へのseekが`FR_INT_ERR`になったため、`Middlewares/Third_Party/FatFs/src/ff.c`のexFAT割当情報設定後に`fp->obj.n_frag = 0`を追加した。CubeMX/FatFs更新後もこの修正の保持を確認する。Debug/Releaseビルド、既存通常/詳細ホストテストが成功し、実機で13100～13103の4本をCSV確定（DONE 100%）、再起動後の未変換bin 0本・復旧完了を確認した。未確定tmpは仕様どおり保持する。ホストテストは模擬FatFsのため、この初期化不良の検証には実FatFsを通るexFATのseek・CSV確定確認が必要となる。

ローカル検証用テストは既存方針どおり `robotrace_v2/tests/` に置き、Git管理対象外とする。

powershell -NoProfile -ExecutionPolicy Bypass -File robotrace_v2/tests/run_log_deferred_tests.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File robotrace_v2/tests/run_pc_tests.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File robotrace_v2/tests/run_log_schema_tests.ps1

新規テストは実際の保存・共通読込・DISTANCE/SLIP/PATH/SHORTCUT実装をRAM上のFatFsで実行する。通常・詳細で、5本の保持と一括変換、走行別メタデータ、記録/メタデータ/ヘッダCRC、予約番号、同番号CSV衝突、残存`.tmp`、短い読書込、同期/クローズ/rename/unlink失敗、再変換を検証する。変更前0b7bda6のCSV第2パスを固定した参照実装と、クロス補正・曲線XY・全CSV行を比較する。

DISTANCEとSLIPは同一パラメータ・一次計画からバイナリ/CSV経由の速度計画を比較する。SLIP比較の各試行前には一次計画を再生成し、前回SLIPの計画をキャッシュとして使わない。曲線経路ではPATH/SHORTCUTの経路点・方位・速度・生成状態が一致することを確認する。
