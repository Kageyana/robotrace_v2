# 全ラインセンサー暗部による完全逸脱停止

2026-10-26、ブランチ`codex/path-curvature-speed`。ユーザー依頼「まずラインを完全に逸脱したときに機体が緊急停止」に対応。

## 変更

- `emergencyStop.c`：中央4個だけの暗部判定を全10個へ変更。全ての正規化値が100未満の状態を1ms周期で数え、20回連続したら停止要求を返す。1個でも100以上なら継続時間を解除する。カウンタは20で飽和する。
- `emergencyStop.h`：`STOP_LINE_LOST_TIME_MS=20U`を追加。閾値`STOP_TH_LINE_SENSOR_UNBRIGHT=100U`は既存の暗部閾値を維持。明部停止の150msカウンタと分離した。
- `timer.c`：暗部停止にあったPATH系の除外を削除。走行中patternTrace11～99は全モード、TRACKINGを含む全経路状態へ適用する。クロスフラグだけで無反応の判定を抑制しない。
- 停止理由は既存の`STOP_LINESENSOR_UNBRIGHT`（emcStop=5）、画面表示`LINESENSOR UB`。既存のメインループで減速・モーター停止・ログ確定・自動走行打切りへ進む。ログ列・保存形式・速度設定・位置補正ゲインは変更しない。

中央だけラインから外れ、端にラインが残る場合は完全逸脱としない。交差部で全センサーが明部ならこの判定では停止しない。PATH系以外の中央4個の明部継続停止は維持する。閾値100～799は今回の「完全暗部」には含めず、以前の解析に使用した明部閾値800以上なしと区別する。

## 確認

実関数と実ISRの停止判定部分を抽出した`validation/emergency_line_loss/run.py`で、O0/O2・Wall/Wextra/Werrorにより以下を検証した。

- モード0～5の19ms未発火・20ms発火、20到達後7万回の呼出しでも飽和維持。
- 各10センサーそれぞれ100の境界で解除、再逸脱時の連続時間の取り直し、走行開始リセット。
- 停止要求後にラインが戻ってもemcStop=5を保持。
- クロス明部500msは停止なし、古いクロスフラグが残る全暗部20msは停止、端だけ明部で500msは停止なし。
- 中央4個の明部停止のモード別既存仕様を維持。

Debug・Release・DebugMarkerのconfigure/buildが成功。既存全体ビルドとの診断文比較で新規warning0。追加処理は固定長10個の読出しとカウンタ更新のみで、1ms内にI/Oやブロッキング処理を追加していない。既存のlSensorCari全10個の公開は割込み禁止下のmemcpyであり、途中配列を制御ISRから読む競合を増やしていない。

ST-Link初回はCore ID取得不能で書込みを行わず、ユーザーが接続を復旧後、100kHz・Under ResetでDevice ID0x421を確認。Debug ELFを書込み、Flash検証・リセット・起動成功を確認した。書込ELFのSHA256は`3e250666ac4121aa0cae4a31d9bea780763a23adeb39e13ca5bd64ef5161b018`。

一致するELFを使い、静止状態の実機で算術判定関数だけを呼び出した。開始要求0・autoStart0・patternTrace0を確認してから、一時的な割込みマスク下でセンサー値を注入。19回までfalse、20回目true・カウンタ20、各10センサーで100の境界解除を確認した。値・割込みマスク・カウンタを復元し、PWM左右0、TIM2 CCR2/CCR3とも0、CFSR/HFSR0でdetach。自分のGDBサーバーを終了した。停止判定の注入試験であり、機体を走行させた検証ではない。

証跡は`build/emergency-line-loss/`のhost-validation.json、build-validation.json、review.json、flash.log、target.raw.log、target.log。新規テスト・生成物は既存方針に従いGit管理対象外。

## 実走行でのユーザー確認

2026-10-26、ユーザーから「実走行でも確認できました」と報告を受けた。完全逸脱時の緊急停止の動作は実走行でも確認済みとする。走行ログ番号・試験回数・停止時間・制動距離は今回の報告では特定していない。

20msは全暗部の検出時間で、停止完了時間ではない。停止時間・制動距離の定量評価と、異なる走行条件での誤停止の評価は別途残る。今回の変更は周回ずれの発生原因や自己位置補正を修正するものではない。
