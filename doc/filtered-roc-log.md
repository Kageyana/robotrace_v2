# フィルタ済み計画ROCのログ列

全走行形式の末尾へ`filteredROC_mm`（U16・mm）を追加した。既存の`ROC`列は速度・角速度による従来値を維持する。

| 走行 | 保存値 |
|---|---|
| DISTANCE/SLIP | 同じ行の`optimalIndex`の`PPAD[index].ROC` |
| PATH/SHORTCUT/PATH_CURVE/SHORTCUT_CURVE | 同じ経路点のフィルタ済み一次半径`lineRoute[index].sourceRadius_mm` |
| 一次・計画なし・範囲外・PATH延長部 | 0（未定義）。曲率半径0という意味ではない |

SHORTCUT系でも、値は一次由来のフィルタ済み半径である。短縮後の幾何半径や操舵FFの先読み窓から逆算した半径ではない。半径は正の大きさで、DISTANCE側の直線は3000、PATH側の直線・上限は32767とする。一次走行中には停止後の計画がまだ存在しないため0を記録する。

`filteredRocMmForLog()`は開始時に固定した方式と、保存する現在インデックスを受け取る。共有RAMの所有権、点数、配列境界を確認し、計画を読むだけで制御状態を変更しない。既存TIM6内のマーカー処理後のログ取得位置で、同じ行の`optimalIndex`と対応させる。1msでのフィルタ再計算は追加しない。

| 形式 | 通常 | 詳細 |
|---|---:|---:|
| 一次/DISTANCE/SLIP | 65列 / 168B | 71列 / 177B |
| PATH系 | 64列 / 179B | 70列 / 188B |

全既存列の位置・型・意味、5mm記録・最大1記録/ms、6144Bの共有I/Oを維持する。保存量は1行あたり2B増える。計算版2は維持し、列定義・スキーマCRCを自動更新する。機体の解析元には更新後に取得する新しい一次ログが必要である。過去のbin/CSVは変更しない。

検証入口はリポジトリルートの`validation/filtered_roc_log/run.py`。通常/詳細・新旧・O0/O2で実getter・writer・readerを使い、7走行ケース×80行を確認した。一次0、現在位置、開始時方式、上限32767、共有RAM所有権、負/0の無効計画、配列末尾、PATH延長部を検査した。独立復号で56ファイル・4480行の全CRC、全既存列の一致、O0/O2完全一致を確認した。CRCが正しい旧形式一次の拒否と、ヘッダ/データ/schema/metadataの各破損拒否も確認した。

実`logPatchPathXYRecords()`による停止後XY補完を通した後も、ROCを含む他の全保存値と全CRCを確認した。保存列のCSVも独立復号で照合した。実`RlogToCsv.exe`はこの環境に未配備であり、実変換器自体の動作は未確認である。自己記述の既存U16列追加なので変換器の仕様上は更新不要である。

Debug/Releaseの通常ログ構成でビルド成功。RAMは89,264/89,336B、Flashは271,664/179,008B。変更箇所に新規warningなし。証跡は`build/filtered-roc-log-20261103/validation.json`と同フォルダの生成C、bin、保存列CSV、ビルドログ。実装時点では実機書込みは未実施だった。その後、11/3の初回実ログ14102（PATH_CURVE、参照一次14098）で追加列・64列7231行・同一indexの一貫性を確認した。0は終端6行だけで延長部の仕様に整合し、一次14098は追加列が全行0だった。元binの全CRCと実C再生成との全点照合は未実施。詳細は`analysis/log_14102_filtered_roc/report.md`を参照する。
