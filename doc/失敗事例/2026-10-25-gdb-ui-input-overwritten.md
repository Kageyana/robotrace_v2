# GDBで注入したスイッチ値を解析要求まで保持できなかった

## 確認した結果と原因

静止中の`setup_log()`入口で`swValTact=SW_PUSH`を注入して続行したが、解析関数の一時ブレークへ到達しなかった。自分のGDBセッションへCtrl+Cを送り、終了を確認した。ファームのFaultやSD処理停止は観測していない。

現行コードではTIM6側の10ms処理が`getSwitches()`で`swValTact`を書き換える。入口での代入が、複数のデバッガ操作後も判定まで残るという前提に問題があった。最初の注入時点の上書き自体はトレースしていないため、その割込み時刻は未確定とする。

## 対処と再発防止

実機上の解析経路確認は、現行ソースで確認した`if (analyze)`直前に停止し、評価済みのローカル変数`analyze=true`を一度指定して通常メイン処理を続行する。スイッチ処理の製品コードや割込みは変更しない。物理スイッチ入力の検証とは区別し、入力・長押し・折返しは実UI関数のホスト検証で確認する。ブロッキングするFatFs関数をGDBの直接呼出しへ置き換えない。

最初は現行ELFの関数シンボルで停止し、行ブレークが必要なときは現在のソース位置と停止時の式を毎回照合する。一度に使うブレークは一点とし、対象の待機が続いたら追加入力を重ねず自分のセッションを終了する。開始要求・自動走行を0に保ち、試験終了時はPWM・TIM2出力0を確認してdetachする。

## 確認方法とステータス

`build/path-curvature-validation/ui-curve2.gdb`と`all-ui.gdb`の終了コード0を確認した。SD上13777の実ログでDISTANCEは467区間、PATHとPATH_CURVEは同じ1181点を生成し、新モード5は1.0～4.0m/sの計画となった。各解析時の`patternTrace=0`、PWM・TIM2比較値0を確認した。修正したデバッグ手順を検証済みとしてresolvedとする。実走行性能を確認したものではない。
