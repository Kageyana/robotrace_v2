# DebugベンチのCSV自己検査が既存形式を誤判定

## 要約

CSVは正常に保存されていたが、自己検査がヘッダー行の位置と列数を誤認して失敗した。

## 発生した状況

- タスク: 56 B/109 BプロファイルのDebugベンチCSV検証
- 実行環境: STM32F446、FatFs、Debug/DebugMarker
- 前提条件: 走行条件メタデータ行が長く、`f_gets()`の固定長バッファを超える。

## 何を試したか

1. メタデータ1行と列見出し1行を読み飛ばす固定手順でCSVを検査した。
2. ヘッダー列数を`LOG_FIELD_LIST`の保存列だけで数えた。

## 結果・エラー

```
メタデータの残りを列見出しとして扱い、CSV行数が期待より1行多く、列数が10と判定された。
修正後はcntlog列で始まる見出しを見つけたが、派生列と末尾空列を含めず検査が失敗した。
```

## 原因

- `f_gets()`は長いメタデータ行を複数チャンクに分割するため、固定行数の読み飛ばしでは列見出し位置を特定できなかった。
- 列数マクロは保存列だけを数えており、CSV変換時に追加する派生列を含まなかった。
- 既存CSVは各行末尾にカンマを持つため、列検査は空の末尾列も含める必要がある。

## 解決・回避策

メタデータを読み飛ばして`cntlog,`見出しを検索し、保存列と派生列の両方を数え、既存形式の末尾空列も検査するよう修正した。通常・詳細の6実機ケースで、行数一致、列数28/47、cntlog単調増加、CSV検証成功を確認した。

## 今後の予防策

- CSV自己検査では固定行数でメタデータを読み飛ばさず、データ列名から見出しを検索する。
- スキーマ由来の列数を作る場合は、保存列と派生列の両方を含め、CSVの末尾区切り仕様も確認する。
- 実機検証では期待行数、読取行数、列数、cntlog単調性を独立して結果へ出す。
