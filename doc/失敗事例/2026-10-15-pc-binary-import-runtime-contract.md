# PC取込ツールの文字コード・モジュール・固定ヘッダ依存

## 2026-10-16 実カード取込の一時的なファイル占有

RT_LOGの実カードから13263～13272を取り込み、13267.csvのMoveで「別プロセスで使用中」が一度記録された。占有元は未特定。確認時にはカードが未接続だったが、tempと保存先の13267.csvが1,919,325 Bで全バイト一致することを確認した。新bin5本も全CRC・行数・列数・保存先一致に成功した。13267のSD側原本削除は未確認であり、次回挿入時の同一内容照合・削除再試行へ残る。データ保全の確認はresolved、占有元とSD側後始末は未確認。

稼働中のmonitor.stdout.txtをFile.ReadAllBytesで開くと共有違反となった。ログ本体の破損ではなく、出力リダイレクト中の共有アクセス制約。稼働中ログはGet-Content、またはFileShare.ReadWriteを指定したFileStreamで読む。ログ読込の共有違反をカード側のI/Oエラーと混同しない。

## 右クリック起動でウィンドウがすぐ閉じる

ユーザーから「PowerShellで実行」のウィンドウがすぐ閉じると報告された。既存のバックグラウンド監視PID 50724が稼働しており、同じセッションのmutexを保持していた。2つ目の起動が未捕捉の「既に起動しています」例外で終了する実装だった。

二重起動は通常の案内として表示し、右クリック相当の対話起動ではEnter入力まで画面を残すよう修正した。起動・実行エラーもcatchで画面と`temp/startup-error.log`へ残す。非表示起動、非対話起動、SourceFolder/Once、明示NoPauseでは待機しない。

Windows PowerShell 5.1で二重起動の案内・終了コード0、Enter前は終了せず入力後に終了すること、非対話の変換器欠落では終了コード1とUTF-8エラーログを確認した。既存監視は保持し、試験用エラーログは試験前の状態へ戻した。Read-Hostのプロンプトだけに出力検証を依存させず、案内をWrite-Hostで明示してから入力を待つ。Explorerの実際の右クリック操作は未実施だが、同じスクリプトの対話起動を再現して修正を検証済み。

再発防止: 常駐ツールは二重起動を未捕捉例外にせず、正常起動・二重起動・起動前エラーを実行確認する。対話と非対話の終了待機を分け、入力待ち検証ではプロセスがEnter前に存続することまで確認する。ツールREADMEにも起動方法と二重起動時の挙動を反映した。

確認事実:

- 固定済み`log_schema_legacy.h`を単独で取り込む初回ビルドで、`LOG_RECORD_SIZE_ADD/SKIP`とプロファイル定義がなく失敗した。列マクロだけのヘッダという仮定が誤っていた。先に型サイズ・プロファイル・サイズ計算マクロを定義して修正した。
- UTF-8 BOMなしの日本語PowerShellスクリプトをWindows PowerShell 5.1で起動し、文字列解析エラーとなった。配布前のBOM確認が不十分だった。UTF-8 BOM付きへ統一し、検証runnerでも実行前に保証するようにした。
- 子Windows PowerShellで`Get-FileHash`が解決できず、隔離取込が失敗した。モジュール探索パス依存が考えられるが、元の探索状態の原因は未特定。SHA256とドライブ検出を.NETへ変更し、モジュール自動読込を不要にした。
- 通常環境の`git -C C:/tool/AutoCopyCsvFromSd status`はPermission denied、必要権限付きでは読み取れた。ファイルの読取成功だけではGitのアクセス成功を保証しなかった。対象外ルートのGit確認・配置は初回から限定した必要権限で行う。
- 監視の初回Start-Processはstdout/stderrの親tempが未作成で、プロセス開始前に失敗した。出力先を先に作成して成功し、同権限で稼働・stderr 0 Bを確認した。通常権限で昇格プロセスが見えないことは終了の根拠にしない。
- 実ログ13085の比較で、同じ保存floatでもfprintfとsnprintfに0.000001の丸め差が出た。旧機体実装と同じsnprintfへ統一し、半端値フィクスチャと実ログのバイト一致を確認した。小さい合成値だけではこの差を検出できなかった。
- 4740行の実ログでは参考RAMモックのf_expand予約上限が3 MiBを超えてassertした。参考変換側だけFR_DENIEDを返す通常割当経路を選んで比較した。製品側の容量制限やデータは変更していない。

再発防止:

1. 固定ヘッダの末尾のenum/static_assertも読み、必要マクロを定義してからビルドする。スキーマCRC・レコード長と全6形式の変換を確認する。
2. 配布用ps1の先頭3バイトがEF BB BFであることを確認し、実際の`powershell.exe -NoProfile -File`で日本語を含む処理を実行する。構文確認だけで完了にしない。
3. 常駐ツールのハッシュ・ドライブ検出には.NETを使う。試験用のSourceFolderによる取込と通常監視の起動を分けて確認する。
4. 互換比較は同じbinを両実装へ渡し、同じCPU・浮動小数点設定で比較する。別の段階で保存されたメタデータやARM対x87の末尾桁差を実装差と決めつけない。
5. 既存ツールをバックアップしてから、検証済みファイルだけを配置・ハッシュ照合する。失敗した取込ではSD原本を保持する。
6. バックグラウンド起動前にリダイレクト先の親を作成し、ErrorActionPreference=Stopで起動失敗を後続へ進めない。新規PIDと同権限の生存確認、stderrを確認する。常駐後の隔離取込テストは同じmutexで拒否されるため、自分の監視だけを停止して実行するか変換器単体テストに限定する。
7. CSV数値の丸め境界を含めて実際の整形APIを比較する。参考ハーネスの予約上限を実ログ長と先に照合し、モック制限を実ログ破損と扱わない。

検証: 固定6形式の新変換器と実ファームウェア変換のPC実行結果がバイト一致。Windows PowerShell 5.1の取込・保存後削除・原本保持・同名衝突/再試行・CRC失敗・旧CSV取込が成功した。設定・tmpの保持も確認。ランタイム対策はresolved、元のモジュール探索環境の原因と実カード取込の動作は別途未確認。
