# 走行別ログ診断の検証前提

- 対象: 一次/DISTANCE/SLIPとPATH系のログ列分離、実writer/readerのホスト検証。
- 確認した結果: 初回Debugは成功したが、独立した匿名enumで定義したレコード長を直接比較するstatic_assertで`-Wenum-compare`が発生した。またホスト生成器は展開前の全マクロ宣言に列名一意性を要求し、DEBUG/CURRENTの排他的な同名電流列で停止した。
- 原因: Cの別enum間比較と、プリプロセッサ展開前の定義一覧を実列一覧と混同したこと。
- 追加確認: 関数抽出の戻り値型を任意文字列にした正規表現が、定義より前のif内呼出を抽出し、ホストC構文エラーとなった。戻り値型・修飾子・ポインタに限定した行頭の関数定義パターンへ修正した。呼出を関数定義として抽出しないことも生成前確認へ含める。
- 追加確認: Pythonのsubprocessを暗黙のcp932でtext読込したため、UTF-8の日本語を含むコンパイル診断でdecodeが失敗し、診断保存も中断した。stdout/stderrはbytesで取得・原本保存した後、表示時だけUTF-8で復号する。後続のコンパイルエラーでも生診断を失わないことを確認する。
- 追加確認: テンプレートの`FF`を順次str.replaceした結果、先に挿入した`CURVE_FF_ENABLE`まで関数本文へ置換した。単語境界付きの単一パス置換へ変更し、挿入済みの実コードへ後続の置換を再適用しない。
- 追加確認: nmのbytes原本を直接復号したCRLF文字列へ行末`$`の正規表現を適用し、末尾CRのため配置照合が失敗した。原本は保存したまま、splitlinesによるLF正規化後に解析する。保存ELFとSHAが一致するnm原本を使い、ビルドや成功済み検証は繰り返さない。
- 同じ改行問題をSkill見出し置換でも確認した。raw decodeしたCRLFへLF固定の見出しを当てたため、保存前assertで停止し、変更は未適用だった。改行を正規化して照合後、元の改行形式・BOMを保って保存する手順へ修正した。
- 対処: 長さの比較をunsignedへ明示変換。宣言用fixtureの同名列は型・式・書式の完全一致を確認して併合し、実列名の一意性は通常/詳細それぞれの展開済み列定義で検査する。
- 再発防止: スキーマの実レコード長・列数・重複検査はビルドprofile×走行方式ごとに展開した定義を使う。匿名enum間のstatic_assert比較は同じ整数型へ変換し、ARMの新規warningがないことを確認する。
- 確認方法: `validation/mode_log_diagnostics/run.py`と通常ログDebug/Release。ホストは各profileのO0/O2で実writer/readerと独立復号を照合する。
- 検証結果: 通常/詳細×O0/O2の実writer/reader・独立復号・全CRC、16000周期の変更前後制御比較、1162581左右目標境界ケースが成功。Debug/Releaseは各65工程の全体ビルド成功、既存6 warning・新規0 warning。共有I/O 6144 Bとスタック予約8192 Bをnm原本から照合。検証中のC構文エラーでも診断原本が保存され、CRLF解析を修正した後はビルドを繰り返さず配置検証だけ再開した。
- 証跡: `build/mode-log-diagnostics-20261101/validation.json`。該当log-analysis Skillの冒頭・実行前手順・再発防止参照とflash-debugの再発防止参照へ反映済み。
- ステータス: resolved。
