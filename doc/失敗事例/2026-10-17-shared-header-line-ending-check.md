# 同内容の共有ヘッダにバイト一致を仮定した

通常/詳細の実CとPC変換器のCSV一致、補正距離変更へのXY不変、旧版・必須列欠落の拒否は成功したが、最後の共有ヘッダのread_bytes()一致検査で停止した。

git diff --no-indexではソース差がなく、改行形式の差が残っていた。文書で「同じヘッダ」としていても、配布済みコピーのバイト一致は保証されていなかった。ファームのlogBinary.hを正としてPCツールへCopy-Itemで配布し、両SHA256の一致と検証スクリプト終了コード0を確認した。実装の計算不具合ではない。

再発防止として、共有ヘッダを更新する際は正のファームヘッダから配布し、ビルド前に配布物のSHA256を照合する。意味の同一性と配布物のバイト同一性を別契約として扱う。書込み・ビルドSkillの成果物事前確認へ追加した。

確認: analysis/xy_raw_distance/validation.json。両ヘッダSHA256=6ded40c90164977d90d7bf66107b0671d9ea9833488841fc23e02461c1c073dc。通常・詳細の機体C/PC CSVバイト一致を含む全検証が成功した。計算版2の初回実機ログは未確認。

## 2026-10-25：binとPC変換CSVのメタデータ比較

タスクはショートカット設定7項目のメタデータ追加。保存済みbinの末尾とPC変換CSVの1行目へバイト一致を仮定した追加assertが停止した。実保存・7項目の開始時保持・CRC検証は既に成功していた。実バイトでCSVの末尾はCRLF、binはLFと確認でき、行末差を試験の比較契約へ含めていなかったことが原因だった。製品の値欠落やCRC不一致ではない。

validation/log_storage/run.pyの比較はCSV側の行末CR/LFだけを除いてLFを付け直し、他の内容は変換せず全メタデータを照合する。次回は文字列の内容一致を要求する前に両形式の改行規約と実バイトを確認し、ヘッダ無変換コピーのバイト一致契約と区別する。書込み・デバッグSkillのPC変換器検証前にも同じ入口を追加する。

確認はリポジトリルート・必要権限で `python validation/log_storage/run.py --converter C:/tool/AutoCopyCsvFromSd/RlogToCsv.exe` を再実行し、通常・詳細両方の全CRC、3種類の設定値の開始後変更からの分離、50行のPC変換値と全メタデータ内容一致が成功した。各プロファイルの結果はbuild/log-storage-validation以下へ保存した。4構成ARMビルドも成功。比較契約の修正はresolved、最初の実機ログは未確認。
